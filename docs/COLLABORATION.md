# DeepSeek 与 Kimi 协作纪律

版本：1.0（2026-10-30）。适用范围：所有在本仓库工作的 AI agent，
当前为 DeepSeek 与 Kimi。用户是唯一的需求、优先级与验收授权来源。

本文件是纪律全文；根目录 [AGENTS.md](../AGENTS.md) 是入口与摘要。
未经用户批准，任何 agent 不得单方面放宽本文件中的约束。

## 1. 三条不可协商

1. **不破坏既有成果**：不 `reset`、不 `checkout --`、不 `clean` 他人的改动；
   不 force push；不删除来源不明的文件。
2. **无证据不宣称能力**：只有当天实际命令输出、结果与产物路径才算验证；
   mock、单测、文件存在、历史报告都不能替代实机。
3. **不静默缩小范围**：TDR-002 的原生电路设计与编辑不可被读取、导出、
   仿真或连接报告替代；禁止 GUI 自动化。

## 2. 角色与默认主责

用户负责需求、优先级、实机验收授权与推送授权。两个 agent 平级，
按域划分默认主责，目的是避免同一文件被同时修改，不是能力限制。

| 范围 | 默认主责 | 说明 |
|---|---|---|
| `core/`、`adapters/authoring.py`、`adapters/kicad/` | DeepSeek | 共享核心、发布边界、KiCad |
| `adapters/multisim/` | Kimi | COM、schema 67、XML 空白保护、探针 |
| `codex-relay/codex_plugin/mcp/` | DeepSeek | 六个工具与安全门禁 |
| `tests/` | 按被测域 | 跨域测试由对应域主责审查 |
| `docs/STATUS.md` | 双方 | 只改自己任务相关的行；结构性改写需双方同意 |
| `docs/WORKBOARD.md` | 双方 | 只改自己的任务行；可自由新增 Proposed |
| `AGENTS.md`、`docs/COLLABORATION.md` | 用户 | 纪律不能由 agent 单方面放松 |

默认主责可以按用户指示调整；调整必须先在 WORKBOARD 记录，再开始工作。

## 3. 任务生命周期

状态只有五种：`Proposed` → `Claimed` → `In Progress` → `Review` → `Done`；
无法继续时标 `Blocked` 并写明原因。

1. **认领前**：运行 `git status --short --branch`。工作区必须干净；
   若有未提交改动，先提交或记录 WIP，不得藏匿他人改动。
2. **登记**：在 `docs/WORKBOARD.md` 写入任务 ID、owner 与验收命令。
3. **直接开发**：在 `dev` 上小步提交，不自行创建任务分支；
   只有用户明确要求时才建分支，并在 WORKBOARD 登记。
4. **执行**：同一时刻每人最多 1 个 In Progress；同一文件只能有一个作者。
5. **自检**：按第 5 节完成验证，更新 `CHANGELOG.md` 与必要的 `STATUS.md`。
6. **提交**：自检通过后直接提交到本地 `dev`，不自行创建任务分支。
7. **复核**：作者不能自审。由另一位 agent 按第 6 节清单复核；
   通过后标 `Done`，发现问题用后续提交修正，不改写已提交历史。
   只有一方可用时，由用户在推送前确认。推送必须得到用户明确授权。

任务范围变化时，先更新 WORKBOARD 再继续；不得“顺手”扩大范围。
阻塞超过一个工作会话，标 `Blocked` 并请用户裁决。

## 4. Git 纪律

- 提交位置：默认直接提交到本地 `dev`，不自行创建任务分支；
  只有用户明确要求时才建分支；`main` 仅用于发布。
- 提交：Conventional Commits。type/scope 用英文，正文可中文。
  每个提交只做一件事，不混入格式化或无关重命名。
- 提交 trailer：必须包含 `Agent: deepseek` 或 `Agent: kimi`。
  仓库本地 Git 身份保持用户指定的 `vista777-nk <1687305011@qq.com>`，不改全局配置。
- 提交前：确认本地 `dev` 未落后于已知远端状态；冲突解决后重新跑验收命令。
- 禁止：force push、改写已推送历史、跨任务混提交、提交本机绝对路径配置、
  提交 `output/`、`.bifrost-authoring/`、厂商模板或任何密钥。
- 推送：默认不推送；仅在用户明确要求时执行。

## 5. 验证与证据

验证分三级，按任务风险递增：

1. **单元/集成（mock）**：目标模块测试通过。
2. **非硬件全量**：`pytest tests/ -m "not hardware"` 全绿。
3. **实机**：`hardware` 标记测试或 `scripts/verify_native_authoring.py`；
   必须使用全新的输出目录，保留产物与 `verification.json`。

能力声明必须包含：

- 改了什么；
- 执行命令与结果（通过/失败数量）；
- 产物路径；
- 未验证项及原因。

禁止用跳过、删除或放宽测试来“通过”。测试失败先定位原因，再修复。
实机测试前确认软件许可、环境变量与用户设备的占用情况
（例如烧录前关闭串口监视器）。

## 6. 审查清单

审查者至少检查：

- 范围是否与 WORKBOARD 一致，有无无关改动；
- 是否触碰红线（GUI 自动化、覆盖原文件、静默丢弃内容）；
- 测试是否覆盖新行为与失败路径；
- 非硬件全量是否通过；
- `CHANGELOG.md`、`STATUS.md`、`WORKBOARD.md` 是否同步；
- 是否引入本机路径、密钥、厂商资产或构建产物；
- 能力声明是否超出证据。

审查意见必须具体到文件与行为；不接受的改动由作者修正后重新审查。

## 7. 文档权威与维护

解释顺序：

1. 用户最新指令；
2. `docs/STATUS.md`（当前事实）；
3. `docs/decisions/TDR-*.md`（已批准的技术决策）；
4. `docs/10-circuit-authoring.md`（当前能力契约）；
5. `docs/WORKBOARD.md`（任务状态）；
6. 其他文档与历史交接（仅背景）。

规则：

- 当前事实只写在 `STATUS.md`，不要在多份文档重复维护。
- `HANDOFF*.md` 是历史快照，不再更新事实；需要更正时在顶部加注并指向 STATUS。
- TDR 一经接受不直接改写结论；范围变化用新 TDR 取代，并在旧文件标注。
- 关键决策不得只留在聊天中；必须落到 TDR、WORKBOARD 或提交信息。
- 文档也遵守“无证据不宣称”。

## 8. 冲突处理

- **文件冲突**：后认领者停止写入，先读对方最新提交，保留双方意图；
  无法合并时交用户裁决。
- **事实冲突**：以可复现命令为准；不可复现的结论降级为“未验证”。
- **优先级冲突**：用户最新指令 > `STATUS.md` 的后续优先级 > WORKBOARD。
- **纪律冲突**：任何放宽（GUI 自动化、覆盖原文件、跳过确认）必须用户书面批准，
  并记录为新的 TDR 或纪律版本。

## 9. 交接与上下文

- 新会话首读：`AGENTS.md` → `STATUS.md` → `WORKBOARD.md` → 相关 TDR/手册。
- 每个任务结束：WORKBOARD 写 `Done` 与证据；能力变化同步 STATUS。
- 会话结束前：确认没有未提交的他人文件；本地提交完成；向用户说明提交与下一步。
- 不依赖聊天历史传递关键信息；聊天只是入口，仓库文件才是记录。

## 10. 对用户与其他 agent 的沟通

对用户固定四段：**现状 / 本次改动 / 验证 / 下一步（含需用户决策）**。
中文、简短、不夸大。

agent 之间通过 WORKBOARD 与提交信息协作；需要对方行动时，在任务行写明
`需要 <agent> 确认`，不要假设对方能看到聊天内容。

## 11. Kimi 启动指令（由用户粘贴）

```text
请先阅读仓库根目录 AGENTS.md，再读 docs/STATUS.md、docs/WORKBOARD.md、
docs/COLLABORATION.md。你是 Kimi，默认主责 adapters/multisim/。

开始前运行 git status --short --branch，确认没有未提交改动；
在 WORKBOARD 认领一个 Proposed 任务，然后直接在 dev 上小步提交，不自行建分支。
遵守红线：禁止 GUI/鼠标键盘自动化；禁止覆盖原始输入；禁止无证据宣称实机能力；
禁止未经用户授权推送。

完成后按 DoD 更新测试、CHANGELOG、STATUS、WORKBOARD，并按
“现状 / 本次改动 / 验证 / 下一步”四段汇报，附命令与产物路径。
```

## 12. 纪律的修改

- 修改本文件或 `AGENTS.md` 必须由用户批准。
- 每次修改在文件顶部更新版本号与日期，并在 `CHANGELOG.md` 记录。
- 纪律条款与用户当次指令冲突时，以用户当次指令为准，并立即更新纪律文件。
